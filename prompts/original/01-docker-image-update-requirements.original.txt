Project: Automated Docker Image Version Upgrade Across Multiple GitHub Repositories

Act as a Senior Python Developer, DevOps Engineer, Docker Specialist, and GitHub Actions Automation Expert.

I need a production-ready Python automation tool that scans multiple GitHub repositories, identifies Dockerfiles, checks Docker image versions, upgrades images to the latest stable versions, and generates detailed reports.

The solution must support private and public GitHub repositories and run automatically through GitHub Actions.

1. Input Configuration

I have an Excel file containing a list of repositories and their corresponding POC (Point of Contact) information.

The Excel file contains the following columns:

Repo_Name
Repo_Link
POC
Email
CC_Email

Each row represents one GitHub repository.

The Python script must:

Read all repositories from the Excel file.
Process each repository independently.
Support private and public repositories.
Authenticate to private repositories using a GitHub Personal Access Token stored in GitHub Actions Secrets.
Process all repositories listed in the Excel file in a single execution.
Generate individual reports for each repository.
Generate one consolidated CSV report for all repositories.

Do not hardcode GitHub tokens, passwords, email addresses, or other credentials.

2. GitHub Repository Access

Use the GitHub API or Git operations to access repositories.

Authentication:

Read GITHUB_TOKEN from environment variables.
Retrieve the token from GitHub Actions Secrets.
Support private and public repositories.
Handle authentication failures, repository not found, permission denied, API rate limits, and network errors gracefully.

Clone or download the repository into a temporary working directory.

Do not modify unrelated repository files.

3. Dockerfile Discovery

Search for Dockerfiles in each repository.

Requirements:

Find files named Dockerfile.
Find files named Dockerfile.dev, Dockerfile.prod, Dockerfile.test, Dockerfile.custom, and similar Dockerfile variants.
Support Dockerfiles located in the repository root.
Support nested folders up to four directory levels.
Support multiple Dockerfiles in the same repository.
Avoid scanning .git, node_modules, vendor, virtual environments, and other irrelevant directories.
Preserve the original directory structure.

Record the relative path of every Dockerfile.

4. Docker Image Version Detection

Analyze every Dockerfile and identify all FROM instructions.

Examples:

FROM node:22.22.0-slim FROM python:3.12.5-slim FROM nginx:1.27-alpine

Support:

Single-stage Dockerfiles.
Multi-stage Dockerfiles.
Multiple FROM instructions.
FROM instructions with AS aliases.
Multiple images in the same Dockerfile.
BuildKit syntax.
ARG variables used in FROM instructions.
Images using digest references.
Images using custom registry URLs.

For multi-stage Dockerfiles, analyze and report every FROM instruction independently.

Example:

FROM node:22.22.0-slim AS builder FROM nginx:1.27-alpine AS production

Both images must be evaluated and updated independently.

Support public container registries, including:

If a registry cannot be queried, mark the image as SKIP with an explanatory reason.

6. Image Upgrade Strategy

For every image, implement TWO independent upgrade strategies.

Strategy A: Latest Stable Patch/Minor Version Within the Existing Major Version

Upgrade the image to the latest stable version while preserving its existing major version.

Example:

Current: node:22.22.0-slim

Possible upgrades: node:22.23.0-slim node:22.23-slim node:22-slim

Select the latest available stable tag that:

Preserves the existing major version.
Preserves the image variant, such as slim, alpine, bookworm, or bullseye, whenever available.
Is compatible with the existing image configuration.
Is not a prerelease, beta, alpha, RC, nightly, or development release.

Prefer a fully specified version tag over a floating major-only tag when available.

Strategy B: Latest Stable New Major Version

Upgrade the image to the latest stable major version.

Example:

Current: node:22.22.0-slim

Possible upgrade: node:26.13.0-slim

Select the latest stable release available at execution time.

Requirements:

Detect the latest stable major version dynamically.
Preserve compatible image variants.
Do not hardcode current versions.
Exclude prereleases.
Prefer fully pinned versions.
Validate that the selected tag actually exists in the registry.

IMPORTANT:

A newer major version can introduce breaking changes.

Do not automatically assume that the application is compatible with a new major version.

For major upgrades:

Generate a proposed upgrade.
Mark the result as MAJOR_UPGRADE_RECOMMENDED or MAJOR_UPGRADE_REQUIRES_VALIDATION.
Allow configurable automatic major upgrades.
Keep automatic major upgrades disabled by default unless explicitly enabled.

Provide configuration options to run:

Same-major upgrade only.
New-major upgrade only.
Both strategies.
Report-only mode without modifying Dockerfiles.
7. Dockerfile Modification

Update Dockerfile FROM instructions while preserving:

Existing formatting.
Comments.
Line breaks.
Stage aliases.
Build arguments.
Platform declarations.
Image variants.
Other Dockerfile instructions.

Example:

Before: FROM --platform=linux/amd64 node:22.22.0-slim AS builder

After: FROM --platform=linux/amd64 node:22.23.0-slim AS builder

Do not update images that are already using the latest appropriate version.

Do not blindly replace text using global string replacement.

Use a Dockerfile-aware parser or a carefully designed line-based parser.

Support FROM references using ARG variables. If a variable cannot be resolved safely, report it as SKIP rather than guessing.

Do not silently change image names, registry hosts, or image variants.

8. Safety and Validation

Before modifying any Dockerfile:

Save the original file content.
Identify the exact FROM instruction.
Verify the new image tag exists.
Confirm the image variant is compatible.
Avoid prerelease versions.
Avoid changing digest-pinned images unless an explicit digest-update policy is enabled.
Prevent downgrades.
Prevent accidental cross-major changes in same-major mode.

After modifying the Dockerfile:

Validate Dockerfile syntax using docker buildx build --check where available, or another suitable validation method.
Optionally run a Docker build when configured.
Record validation results.
If modification or validation fails, restore the original Dockerfile.
Never leave a partially modified Dockerfile.

Do not commit changes automatically unless explicitly configured.
